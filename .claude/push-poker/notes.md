# push-poker 開發筆記（給 AI／維護者看，非玩家說明）

給人看的版本在 [../../push-poker/攻略.md](../../push-poker/攻略.md)。這份放腳本用法、實作細節、除錯教訓、演算法調校過程。

## 使用 `autoplay-bot.js`

1. 開啟遊戲首頁即可（不用先手動選模式／猜拳，腳本會自己來）。
2. 想指定難度就先改腳本開頭的 `CONFIG.difficulty`（`'easy'` 簡單／`'hard'` 困難，預設 `'hard'`）。
3. 打開 DevTools Console，貼上整份 `autoplay-bot.js` 並執行——**貼上就會自動開始**：自動選難度、按開始對戰、隨機出拳猜拳（平手自動重猜），接著自動對戰到分出勝負，不用再手動呼叫任何東西。若腳本是中途貼上的（已經在對局中），前面選單/猜拳步驟會自動跳過，直接接續對戰邏輯。
4. 分出勝負後想再自動打一場，呼叫 `pushPokerBot.run()` 即可（內部有加鎖 `running`，腳本還在跑時重複貼上或誤呼叫 `run()` 不會啟動第二個迴圈搶按鈕）。
5. 也可以呼叫 `pushPokerBot.step()` 手動走一步、觀察它的判斷（回傳目前雙方在中央的張數與剛剛選的拆法+分數）；但 `step()` 不會處理選單/猜拳畫面，要先確定已經在對局中，且自動遊玩迴圈沒有在跑。
6. 常用查詢：
   ```js
   pushPokerBot.getCenter()   // { my: Set, opp: Set } 目前中央哪些格子是誰的
   pushPokerBot.isMyTurn()    // 目前是不是我的回合
   pushPokerBot.config        // { difficulty: 'easy' | 'hard' }，跑之前可以改
   ```

## 演算法調校過程：稀有度權重是怎麼調出來的

`攻略.md` 裡「優先搶稀有牌」這條策略，舊版程式的實際算分沒有真正做到——`autoplay-bot.js` 舊版有一個「自己已經領先時加速衝刺」的加分項，是用**這步移動的張數 × 目前已進中央的張數**去加分，跟牌的稀有度完全無關。遊戲玩到中後段（`my.size` 變大）時，這個加分項的量級會蓋過稀有度差距，導致骰到 6 時寧可選「拆 1+2+3」湊三張，也不選「直接用 6」留住這張全場唯一入口的稀有牌——白白放掉整局唯一能拿 6 的機會。這是實際玩過後才發現的問題。

已經修正：自己搶牌的權重把 1 直接歸零（`grabRarity`，對手推回時仍用原本的稀有度權重，因為推回對手的稀有牌一樣重要），「加速衝刺」的量級也大砍到只剩極小的同分判斷用途，不會再蓋過稀有度。

修完上面那條之後，玩下一局又抓到第二個同類型的問題：**自己的 6 明明還在（沒被拆出去），骰到 6 卻選了「拆 4+2」而不是「直接用 6」**。原因是推回對手的加分權重（`1.5 * P 的稀有度總和`）沒有分「推回幾張」，只推回對手單獨一張普通的牌（例如對手的 2），也一樣套用 1.5 倍的高權重，湊起來就足以蓋過「直接用 6」的稀有度分數——但「多張淨牌差才划算」的原始例子（`1+2+3` 一次推回對手 3 張）講的是**多張**才划算，不是任何一張都值得。第一次修正把單張推回的權重從 1.5 倍降到 0.5 倍，`P.length >= 2` 才維持 1.5 倍；`opp.size >= 3` 的防守優先邏輯不受影響（那條本來就是獨立判斷，不看推回幾張）。

降到 0.5 倍後，寫了 [check-scoring.js](check-scoring.js) 窮舉所有骰值 × 拆法 × 對手推回組合離線驗證，發現 0.5 倍還是不夠：只要對手剛好有一張 4 被單獨推回，還是會蓋過「直接用 6」（6 是全場唯一入口，賠不起）。再降到 0.35 倍後窮舉全部通過，只剩兩種確認過不是 bug 的案例——骰到 3 選 1+2、骰到 5 選 2+3 或 1+4，即使對手完全沒有牌可推回也一樣選拆兩張。這是因為 2 跟 3、4 跟 5 分別同一個稀有度等級，放棄的那張跟拿到的那張稀有度打平，「多拿一張幾乎免費的 1」數學上不虧，跟 6 那種「這次不拿、很久都拿不到」的情況本質不同；玩家本人確認過這兩種留著不用管。**之後如果再調整算分權重，重新跑一次 `node .claude/push-poker/check-scoring.js`，只要沒有冒出這兩種已知案例以外的可疑結果就沒問題。**

## 腳本實作細節（踩過的坑）

- **`button.opt` 不是只有輪到我才會出現**：電腦回合時，畫面會顯示「電腦決定這樣走」的預覽，用的是同一個 `button.opt` class！一開始沒檢查回合歸屬，腳本誤點了電腦的決策預覽，導致行為錯亂、也污染了不少回合紀錄。**務必先用 `document.body.innerText.includes('你的回合')` 確認輪到自己，才能去找 `.opt` 按鈕。**
- **拆法按鈕的文字格式不只一種**：「直接用 X」、「折成 X+Y」、「拆 X+Y，Y 已在中央」……格式不統一，靠關鍵字比對容易漏。穩定作法：把文字用「推回」切開取前半段，再用正規式 `/[1-6]/g` 掃出所有數字，就能涵蓋所有格式拿到完整拆法組合。
- **骰子動畫有延遲**：擲骰子後 `button.opt` 不會馬上出現，單次 `sleep` 常常抓到空陣列造成「沒有合法移動」的假訊號。一開始改成固定間隔迴圈重試才穩定，後來又因為背景分頁的節流問題整個換成 `waitForChange`（見下一條），不再是單純輪詢。
- **背景分頁會讓固定輪詢的腳本「看起來停住」，要參考 2048 那份腳本的作法**：Chrome 分頁切到背景後，`requestAnimationFrame` 會被直接暫停（完全不觸發），`setTimeout` 則是被節流到大約每分鐘才醒一次（`.claude/2048/notes.md` 記錄過這個坑）。一開始跟 2048 一樣全部只用 `setTimeout`（不用 rAF），但還是不夠——舊版每一步要串好幾個 `sleep`／重試迴圈才能等到畫面變化（擲骰後最多重試 20 次、等電腦回合固定 `sleep(300)`），節流狀態下等於一步要熬過好幾輪「每分鐘一次」，體感上跟完全停掉沒兩樣，這是使用者實測回報的問題。修法是把這些等待改用 `waitForChange()`：內部掛 `MutationObserver` 等 DOM 真的出現變化就立刻 resolve，不吃 Chrome 這套計時器節流預算，只有等不到變化時才靠底下一顆保底 `setTimeout` 逾時放棄；這樣「輪到我了嗎」「拆法選項出現了嗎」都能幾乎即時反應，不會被自己輪詢的頻率拖慢。唯一無法繞過的是網站自己內部的計時器（例如電腦「思考」的固定延遲）——那是它自己排的 `setTimeout`，一樣會被 Chrome 節流，這塊我們控制不到，但至少不會再被我們自己的輪詢邏輯雪上加霜。
- **中央格子的擁有者**：讀 `.slot .card` 的 `aria-label`（例如「你的 3」/「電腦的 3」），比看卡片花色顏色可靠——花色圖示在小尺寸截圖上紅心/黑桃、數字 1 和 4 的字體很容易看錯。
- **破壞動畫可以放心加速**：檢查過打包後的原始碼（`assets/index-*.js`），畫面上的骰子/推牌/燒灼特效都是純 CSS `transition`/`animation`（0.2~1.2s 不等），遊戲邏輯完全沒有掛 `animationend`/`transitionend` 監聽去等動畫播完才切換狀態。所以腳本一開局就注入一段 `* { animation-duration/transition-duration: 0.001s !important }` 的 `<style>` 把所有動畫砍到接近 0，畫面秒切，且不影響任何遊戲邏輯；連帶把原本保守抓的 `sleep`（400/600/900ms）都縮短（150/200/300ms），肉眼可見跑得快很多。
- **難度按鈕、開始對戰按鈕都是純文字比對**：首頁未開局時，`button` 的 `textContent.trim()` 剛好就是 `簡單` / `困難`，開始鍵是 `開始對戰`，不用額外挑 class。
- **搶牌算分跟推回算分要分開兩套權重**：一開始兩者共用同一份 `rarity` 表，結果「加速衝刺」加分項（張數 × 已進中央張數）在中後盤蓋過稀有度差距，出現寧可拆 1+2+3 湊張數也不留稀有 6 的錯誤決策。修正後自己搶牌用 `grabRarity`（1 歸零），推回對手仍用 `rarity`，「加速衝刺」也砍到只剩 `N.length * 0.5` 這種極小的同分判斷用途。
- **猜拳按鈕有乾淨的 `data-rps` 屬性**：`button[data-rps="ROCK"|"SCISSORS"|"PAPER"]`，比對文字（`石石頭`/`剪剪刀`/`布布`，圖示字＋說明字黏在一起）可靠很多。平手時同一批按鈕會重新出現、可以重猜；判斷「猜拳已分出勝負」只要看 `button[data-rps]` 是否還存在於畫面上即可，不用解析訊息文字。

## 大樣本驗證（簡單/困難各 10 場）

用瀏覽器分頁背景注入 `autoplay-bot.js` 的邏輯（非貼原始腳本，而是把同一套 `step()`/算分邏輯搬進頁面內用迴圈連續跑 10 場、跑完自動點「再來一局」續下一場），簡單、困難各打 10 場，驗證改過權重後的腳本在大樣本下的真實勝率。

**簡單模式（10 場，9 勝 1 敗）**：步數 18/19/23/38/53/55/58(敗)/80/127/165。

**困難模式（10 場，1 勝 9 敗）**：步數 26(勝)/32/37/39/44/56/126/127/183/188。

**結論：**

- 簡單模式下這套算分邏輯幾乎穩贏（90%），跟小樣本測試時的印象一致。
- 困難模式實際勝率只有 10%，遠低於早期只打 3 場時「看起來還行」的印象——3 場的樣本量太小，不能代表真實勝率。
- 困難模式的電腦回推判斷明顯比簡單模式強很多，同一套「對手 ≥3 張強制防守」＋「避免自曝 1+2+3」的策略在困難模式下不夠用，多數場次會在中後段被電腦一次團滅逆轉（觀察到好幾場輸的對局都是自己一度 4~5/6 領先，被電腦一次推回 3 張以上直接翻盤）。

**背景分頁節流備忘**：兩個 tab 同時背景跑（沒有 OS 前景焦點）時，就算把網站加進 Chrome「一律啟用這些網站」清單，還是會被明顯節流——單次 CDP `Runtime.evaluate` 呼叫常常在 20~30 秒內就等到 45 秒逾時，但遊戲邏輯本身沒有卡死，只是變慢；用 `computer` 工具截一次圖（強制排一次 repaint）通常能讓卡住的畫面立刻更新到最新狀態，可以拿來當「這局到底有沒有在動」的診斷手段。

## 困難模式改用官方演算法（逆向自 assets/index-*.js）

10 場只贏 1 場之後，玩家問「上網查得到遊玩技巧嗎」——查了發現這是玩家自己架的小遊戲，網路上完全沒有資料。但頁面footer寫著「規則引擎、電腦對手…都直接來自 src/」，代表困難 AI 的真正邏輯就在前端打包檔裡，可以直接讀出來，不用再靠黑箱猜。

**怎麼找到的**：`curl` 抓下首頁 `<script src>` 指到的 `assets/index-*.js`（單檔約 50KB，minified），用 Node 讀檔案字串搜尋 `"困難"`、`"difficulty"` 兩個關鍵字定位到呼叫困難 AI 的地方：

```js
computerStep(e){ ... let t=this.mode.kind===`ai`?this.mode.difficulty:`easy`;
  this.botIntent=Mt(this.state,e,t,this.rng), ... }
```

追進 `Mt`／`Nt`／`T` 三個函式（縮到只剩單字母，但邏輯完整可讀），還原出來的規則：

- **`jt`（稀有度表）**：`jt[n] = 6 / (能移動這張牌的骰法種數)`。實際算出來是 `{1:1.2, 2:1.5, 3:1.5, 4:2, 5:3, 6:6}`——形狀跟我們手調的 `rarity` 表很像（數字越大代表牌越稀有），但數值不同，而且官方**不是拿去當每一步的加分權重**，是拿去算整體盤面分數。
- **`T`（盤面分數）**：`我方中央牌的 jt 總和 − 對方中央牌的 jt 總和`；一方六張全進中央則整體再 `±1000`。
- **`Mt`（困難模式選拆法，也就是每一步的決策入口）**：對每一種目前可選的拆法，模擬「選這個拆法之後」的盤面，如果模擬完自己就贏了直接給 `T` 分數；否則丟給 `Nt` 算「期望值」，取期望值最高的拆法（同分才隨機選）。
- **`Nt`（期望值：往前看對手下一擲）**：窮舉對手下一擲的 6 種骰值（每種機率均等，就是真骰子的機率），對每種骰值：如果對手當下沒有合法拆法（跳過回合），直接用目前盤面的 `T` 分數；如果對手有合法拆法，假設對手會「貪心」選出**對他自己**分數最高的那個拆法（只往前看一步，不會再往下遞迴），套用之後再用 `T` 算回我方視角的分數。6 種骰值的分數平均起來就是期望值。

簡單講：官方困難 AI 不是「防守門檻 + 稀有度加權」這種經驗式規則，是每一步都做一層 expectimax（模擬自己這步 → 窮舉對手下一擲 6 種骰值 → 假設對手貪心選出對他最有利的拆法 → 取期望值最高的選項）。這比我們原本的經驗式權重精準很多，也是它會贏那麼多的原因。

**做的事**：把 `Mt`／`Nt`／`T` 原封不動搬進 `autoplay-bot.js`，角色對調用在我方身上（見腳本裡 `HARD_RARITY`／`hardScore`／`expectedAfterOpponentTurn`／`chooseHardMove` 幾個函式），困難模式從「自己想的經驗式打法」換成「跟電腦用同一套官方演算法互打」。技術上不需要真的還原出「骰到幾點」——因為 `Nt`／`Mt` 從頭到尾只用到「這個骰值能拆出哪些牌」這個子集合，畫面上按鈕解析出來的拆法本身就已經是這個子集合，所以直接餵給 `chooseHardMove` 就好，省了一層容易出錯的「反推骰值」。

**重新驗證（困難模式 10 場，換算法後）**：3 勝 7 敗，勝率從舊版經驗式權重的 10% 提升到 30%。步數：66(敗)/87(敗)/129(勝)/84(勝)/143(敗)/21(敗)/45(敗)/35(勝)/86(敗)/26(敗)。

**還沒完全打平的可能原因**（雙方用同一套演算法照理應該接近五五波，但目前只有 30%）：
- 樣本量還是偏小（10 場），二項分布下真實勝率落在 50% 時，10 場只贏 3 場以下的機率本身就有一定機率發生，不算離譜到一定有問題。
- `Nt` 只往前看 1 步（自己這步 + 對手下一擲），沒有更深的遞迴；雙方用同一套 1 層搜尋理論上應該對稱，但沒有交叉驗證過我方腳本跟官方數值逐步比對是否每一步都完全一致，不排除還有沒抓到的細節差異。
- 猜拳先手是隨機的，先手優勢可能沒有被這 10 場的樣本平均掉。

若之後要再挑戰更高勝率，方向是：把 `Nt` 從 1 層擴展成多層遞迴（正牌 expectimax，往下模擬好幾個回合），或者既然狀態空間不大（雙方中央牌各自最多 64 種組合），可以考慮直接做逆向歸納法把整個遊戲解出最優解，而不是繼續在 1 層搜尋上打轉。

## 這件事帶來的一般性心得

- **UI 上長得一樣的按鈕，不代表語意一樣**：這款遊戲把「玩家的操作選項」和「電腦的決策預覽」用同一個 class 渲染，寫自動化腳本時一定要先確認狀態歸屬（回合、模式）再篩選可互動元素，不能只憑 CSS selector 判斷「這是不是我能點的東西」。
- **用正規式抓資料時，先讓格式的『共同鉤子』（這裡是『推回』這個詞）當切割點，再抓數字，會比窮舉所有措辭組合更穩健**，尤其是像這種同一個資料點會有好幾種自然語言包裝的情況。
- **push-your-luck 型遊戲的策略評估要包含「防守優先序」與「自曝風險」兩個維度**，不能只算「這步能拿多少」，還要算「這步會不會讓自己更容易被一次性團滅」。
