# 2048 開發筆記（給 AI／維護者看，非玩家說明）

給人看的版本在 [../../2048/攻略.md](../../2048/攻略.md)，裡面有通用技巧、這個專案玩家本人的角落+蛇形+顧尾巴打法、以及自動遊玩腳本的簡介。這份放程式碼層級的細節：網站結構還原、演算法效能優化過程（含實測數據）、腳本用法、除錯心得。外部優化建議報告原始檔在 [優化建議/](./優化建議/)。

## 遊戲本體與程式結構

同一作者（ychung1998）的另外兩款（gomoku、othello）都是「棋盤邏輯 + UI」分離的乾淨架構，這款也一樣：

| 檔案 | 內容 |
|---|---|
| `game-logic.mjs` | 純函式核心：`createEmptyBoard`、`addRandomTile`、`move(board, dir)`、`hasWon`、`canMove`，SIZE=4，無 DOM 依賴 |
| `tile-animator.mjs` | 純函式動畫狀態機，決定方塊 DOM id 該在哪裡 |
| `script.js` | 接鍵盤/觸控事件、呼叫 `game-logic.mjs`、操作 DOM、存 `localStorage` |

**關鍵差異（跟 dino 版不一樣）**：`board`、`score` 是 `script.js` 這個 ES module 內部的區域變數，**沒有掛在 `window` 上**，Console 打 `board` 或類似變數名稱都拿不到（不像 dino 遊戲有 `Runner.instance_` 這種公開全域物件）。要讀盤只能反推 DOM：

```js
// 每個 .tile 元素：dataset.v 是數值，style.left/top 是像素座標
// tileGeometry(): padding=10, gap=10, cellSize=(棋盤寬-20-30)/4
// 用這個公式把 left/top 換算回 row/col，見 autoplay-bot.js 的 readBoard()
```

按鍵一樣可以用標準 `KeyboardEvent` 直接 dispatch，這個網站的 handler 只讀 `e.key`（`ArrowLeft/Right/Up/Down`），不需要像 dino 版那樣處理唯讀的 `keyCode`：

```js
document.dispatchEvent(new KeyboardEvent('keydown', { key: 'ArrowLeft', bubbles: true, cancelable: true }));
```

## 能不能「破解」？（分析結論，完整版）

使用者的直覺是對的——**新方塊的生成是真隨機，破解不了**：

- `addRandomTile(board, rng = Math.random)`：位置用 `Math.random()` 從空格陣列隨機選一格，數值 90% 是 2、10% 是 4，`rng` 參數只有測試時會注入固定值，正式頁面就是原生、未加種子的 `Math.random()`。沒有弱 PRNG、沒有可預測的種子、沒有能操縱下一顆數字的漏洞。
- 沒有找到像 dino 版網站那樣自帶、可以直接借用邏輯的「AI/機器人模式」。
- 唯一「技術上」可動的手腳，是**顯示用的紀錄本身完全沒有校驗**：
  - `localStorage['2048-best-score']`：最高分，`Number` 存字串，沒有簽章、沒有跟伺服器對過帳。
  - `localStorage['2048-history']`：最近 20 局紀錄（時間、分數、輸贏）。
  - 兩者都可以直接在 Console 竄改，例如 `localStorage.setItem('2048-best-score', '999999999')`，畫面上的「最高分」就會變成假的。但這只是騙自己瀏覽器的顯示，不是破解遊戲邏輯，純作弊沒有意義，**攻略腳本沒有用這條路**，走的是正規 AI 演算法硬算。

## 使用 `autoplay-bot.js`

1. （可選）貼之前先改腳本開頭的 `TARGET_SCORE`，改成你想衝到的分數（例如 `const TARGET_SCORE = 50000;`），預設 `Infinity` 代表不設上限、一路重試下去。
2. 打開遊戲頁面，開啟 DevTools Console。
3. 貼上整份 `autoplay-bot.js` 並執行。
4. 腳本會自動判斷方向並模擬按鍵；達成 2048 跳出「繼續」彈窗會自動按繼續；單局「遊戲結束」會自動點重新開始、接著玩下一局；只有分數真的達到 `TARGET_SCORE` 才會整個停止。
5. 常用查詢：
   ```js
   window.__2048BotLog             // 每局結束/達標的分數紀錄（最近 30 筆）
   window.__2048BotMoves           // 目前已走步數（累計所有局）
   window.__2048BotAttempts        // 已經玩完幾局
   window.__2048BotBest            // 目前所有局裡的最高分
   window.__2048BotRerolls         // 累計悔棋重骰次數
   window.__2048BotTarget = 50000  // 不用重貼腳本，執行中也能改目標分數
   ```
6. **暫停/繼續**：
   - 暫停：`window.__2048BotStop = true`，跑完當下這一步就停，盤面、分數都還在，不會清空重來。
   - 繼續：只要**同一個分頁沒有重新整理過**（腳本的變數還在），打 `window.__2048BotResume()` 就會接著暫停時的盤面繼續玩，不用重貼腳本。
   - 如果分頁重整過或整個關掉重開，腳本的變數會消失（因為只存在瀏覽器記憶體，沒有寫進任何檔案），必須重新貼一次整份 `autoplay-bot.js`；但這只是腳本要重新啟動，遊戲本身的最高分紀錄是存在 `localStorage`，不會因此不見。

## Turbo 引擎 + Turbo 動畫（依實測結果強化搜尋速度、壓縮動畫時間）

有人拿另一個 AI（Gemini）針對「2048 演算法效能優化」給的建議截圖（原始檔見 [優化建議/](./優化建議/)），要求依內容強化 `autoplay-bot.js` 的演算法，並且「破壞動畫時間來加快玩的速度」。兩件事都做了，但重點是：**每一項都先在 Node / 瀏覽器裡實測驗證過，不是照抄截圖裡的數字**。

### 1. 搜尋引擎優化（只動引擎內部，不動角落/蛇形/顧尾巴的評分邏輯本身）

1. **零記憶體配置滑動核心**：原本 `transpose`/`reverseRows`/`filter` 疊好幾層陣列映射，改成 `LINES` 表 + 共用 scratch 緩衝，直接用索引運算滑動合併。用 80 萬次隨機盤面 x 4 方向跟舊版逐格比對，**完全一致（0 mismatch）**才換上來。
2. **BigInt 盤面雜湊**：方塊都是 2 的冪，用 `clz32` 算 exponent（5 bit/格），16 格打包成一個 `BigInt` 當 `Map<bigint, number>` 的鍵，取代原本每個節點都要拼字串的 `boardKey()`。
   > ⚠️ **這一項後來被推翻了**：BigInt 雖然比拼字串快，但在 V8 裡每個運算都要配置堆積物件，實測仍是整個搜尋最貴的一段。第二輪改成兩個原生 32-bit 整數後又快了一個量級，見下面第 4 節。
3. **深層分支機率剪枝**：機率節點空格數 > 6 時，只對「最貼近現有方塊」的 6 個空格完整展開 2/4 兩種分支，其餘空格只展開機率占多數的 2（跳過 4）。
4. **保證最小搜尋深度（depth 4）**——這裡踩到一個真的坑，老實記錄：

   最早直接照搬截圖的做法「depth < 4 不檢查時間、一定跑完 depth 4」，結果在瀏覽器實測時，一步棋衝到depth 9、單步耗時 1.4 秒（比完全沒有這個保證深度機制的舊版還慢很多）。原因是：iterative deepening 只在「一整輪跑完之後」才檢查時間，但 depth 每 +1，一輪的耗時可能暴增 3~5 倍甚至更多（實測同一個 11 空格的早期盤面：depth7=105ms、depth8=294ms、depth9=1424ms）——只在輪與輪之間檢查，擋得住「要不要開始下一輪」，擋不住「這一輪自己就暴衝」。

   修法：開始下一輪之前，先用「上一輪耗時 x 保守成長倍數 4」預測這一輪大概要多久，預測會爆預算就直接不跑，不是跑完才後悔。修好之後單步時間穩定控制在預算內，不會再暴衝。（當時的預算是一般 120ms、異常盤面 300ms；後來依第 5 節的實測砍成 25ms / 60ms，`MIN_GUARANTEED_DEPTH` 也從 4 提到 6。）

實測結果（Node，`engine-bench.js`）：跟舊版（2D 陣列 + 字串 key）比較，depth 4~7 大約快 **2~2.6 倍**（空格多的早期盤面剪枝效果更明顯），depth 4 兩版選的方向在抽樣測試裡 100% 一致。這裡老實報告實測數字——截圖裡「20 倍」「毫秒級」是別的（未知）情境下的說法，沒有在這個網站的真實盤面上驗證過，不能直接套用。

### 2. 讀盤時機：從「猜一個固定毫秒數」改成「偵測 DOM 穩定」

一開始的做法是「把 CSS 動畫壓到接近 0 + 讀盤前固定 `sleep(40ms)`」，但這其實踩到一個容易忽略的風險：`readBoard()` 讀的是 `.tile` 的 inline `style.left/top` + `dataset.v`，**這些是網站 JS 一算完新盤面就直接設定的目標值**；CSS transition/animation 動的只是「畫面上怎麼從舊位置滑到這個目標值」，跟 inline style 本身的數值沒有必然關係。

也就是說「固定 sleep 多久才安全」本來就是用猜的：猜太保守（170ms）浪費時間，猜太激進（例如壓到 5ms，通常連一個 `requestAnimationFrame` 更新週期都不到）就可能在網站 JS 還沒把新方塊/新位置寫進 DOM 前搶先讀盤，讀到「少一顆方塊」或「還是上一步的舊盤面」——等於用速度換正確性。

所以改成主動偵測、不猜數字：`waitForBoardSettle()` 每個 `requestAnimationFrame` 都比對一次「所有 `.tile` 的 left/top/v 組成的簽章」，**連續兩個影格都沒變**才視為盤面真正穩定、可以安心讀盤。不管網站內部是同步更新還是分好幾個影格更新完，都保證不會讀到一半；同時因為不用死等一個保守的固定值，實際只要 1~3 個影格（約 16~50ms）就回來，比任何固定延遲都更貼近真正的物理極限。`SETTLE_MAX_WAIT_MS`（250ms）是保底上限，避免分頁被瀏覽器背景節流時卡死在無窮等待。

CSS 動畫壓縮（壓到 `0.01s`）保留下來純粹是讓畫面看起來也同步變快，**讀盤正確性不依賴它**。刻意不是 `0s`——CSS Transitions 規格對 duration:0 的 transition 不保證觸發 `transitionend`，遊戲若拿這個事件排程下一步，設 0 反而可能卡住。`FAST_ANIMATIONS` 設 `false` 可以關掉這個視覺效果（例如想錄影展示原本動畫節奏），不影響讀盤邏輯。

### 3. 實機驗證（用 Claude in Chrome 打開真實頁面測試，不是紙上談兵）

- 確認 CSS 有生效：`getComputedStyle(tile).transitionDuration` 讀到 `0.01s`。
- 分頁在背景（`document.hidden = true`）時，Chrome 會把 `setTimeout` 節流到大約每秒 1 次，量到的速度只有 0.5 moves/sec——這是瀏覽器背景分頁節流機制造成的假象，不是腳本問題，新舊版都會被同樣節流。
- 分頁真正在前景可見時，實測 **19 秒跑了 156 步、分數衝到 1268**，約 **8.2 moves/sec**（舊版 170ms 延遲的理論上限約 5~6 moves/sec）；單步最慢時間穩定在幾百毫秒內（有保證最小深度的修 bug 版本），沒有再出現秒級暴衝。
- 跑了兩局（一局輸掉自動重開），腳本的重開/悔棋機制正常運作；悔棋（重骰）次數偏高（同一時段 353 步裡悔棋 128 次），這是「顧尾巴」heuristic 本身既有的行為，這次的 Turbo 修改沒有動這套判斷邏輯，數字供之後想調整這套 heuristic 時參考，不在這次「加速引擎、加速動畫」的範圍內。

### 4. 第二輪引擎強化：拔掉 BigInt、共用快取、全程零配置（含實測數據）

第二輪的目標是「強化演算法讓分數更高」。做法是先量測、再動手，結論有好有壞，這裡連同「沒有變好的那一半」一起老實記錄。

#### 先量測：時間到底花在哪

用 `scratchpad/profile-parts.js` 在真實盤面上量每個熱點的單次成本：

| 熱點 | 單次成本 |
|---|---|
| `evaluate()`（評分，只在葉節點呼叫） | 240 ns |
| `simulateMove()`（滑動一個方向） | 1099 ns |
| BigInt 雜湊 + Map 存取（每個內部節點都要） | **1796 ns** |
| 改用兩個 32-bit 整數 + 巢狀 Map | **87 ns** |

> ⚠️ **量測陷阱（差點害我改錯地方）**：第一版把腳本程式碼直接丟進 vm 的**全域**作用域測，`evaluate()` 量到 6764ns、看起來是最大瓶頸。實際上那是假象——真正的腳本整個包在 IIFE 裡，變數是 closure 變數；丟到全域會變成 global lexical binding，V8 解析慢得多，而 `evaluate()` 剛好碰最多這種變數（每次呼叫要查十幾個常數 + 呼叫 `weightedValue()` 二十幾次）。改成「用一個 function 包起來、重現原本的 IIFE 作用域」之後重量，`evaluate()` 只要 240ns，瓶頸其實是雜湊跟配置。**量測環境跟實際執行環境的作用域結構不一樣，量出來的數字就是錯的。**

#### 改了三件事

1. **拔掉 BigInt 盤面雜湊**（1796ns → 87ns，約 20 倍）：exponent 每格 4 bit、8 格打包成一個 32-bit 整數，整個盤面 = lo/hi 兩個整數，快取改成 `(剩餘深度,回合) → lo → hi → 分數` 的巢狀 `Map`，全程只用原生 32-bit 運算。（65536 以上 4 bit 裝不下，偵測到就跳過快取，不會拿到撞鍵的錯值。）這跟同專案黑白棋 bitboard 改寫的結論一致：**在 V8 裡用 BigInt 做位元運算是陷阱**，每個運算都要配置堆積物件，實測比普通陣列還慢。
2. **iterative deepening 各輪共用快取**：鍵值本身就含「剩餘深度 + 輪到誰」，而 `(盤面, 剩餘深度, 回合)` 唯一決定該節點的值，所以深一輪可以直接命中淺一輪算過的子樹。原本每輪都 `new Map()` 重來，等於把前面每一輪的成果全部丟掉。
3. **搜尋樹全程零記憶體配置**：每層深度各自持有一塊暫存盤面/空格清單/criticality 陣列，同層分支輪流覆寫。安全性來自「每個節點只寫自己這層、只讀上一層」，而子節點的剩餘深度必定小 1，所以子樹永遠不會動到父節點正在讀的那塊。連機率節點的 `cells.map().sort().slice()` 也換成就地插入排序（刻意保持與 `Array.sort` 相同的穩定性，同分維持格號順序，結果才會與舊版完全一致）。

#### 驗證：改完的搜尋結果與舊版逐一比對完全相同

速度優化最怕「順便改到行為」，所以先證明**只有速度變、決策沒變**：

- `simulateMove`：30 萬個隨機盤面 × 4 方向 = **120 萬次比對，0 筆不一致**。
- `search()` 回傳值：2691 個真實對局盤面（涵蓋空格 0~14，兩個剪枝分支都走到），深度 3/4/5 各比一輪，共約 **2.3 萬個方向分數，全部 bit-identical，選擇的方向 0 筆不同**。

#### 成果：快 2.6~3.3 倍，同樣時間預算多搜約 1 層

| 固定深度 | 舊版 ms/步 | 新版 ms/步 | 加速 |
|---|---|---|---|
| depth 4 | 7.42 | 2.55 | 2.91x |
| depth 5 | 39.07 | 11.95 | 3.27x |
| depth 6 | 78.39 | 30.11 | 2.60x |

拿真正會跑的、有時間預算的 `bestMove()` 在 122 個真實盤面上量「實際搜到第幾層」（跑兩輪確認可重現）：

| | 平均搜到的深度 | 深度分布 |
|---|---|---|
| 舊版 | 6.50 / 6.54 | 有 5~9，眾數 6，**會掉到 5** |
| 新版 | 7.39 / 7.47 | 只有 6~9，眾數 7，**不曾低於 6** |

注意兩版的單步耗時都還是 ~150ms：iterative deepening 本來就會把時間預算用好用滿，**所以加速換到的是「深度」，不是「每秒步數」**。

#### 但是：分數在深度 5 之後就飽和了（誠實的壞消息）

用固定深度跑完整對局（同一組種子、配對比較，悔棋機制照常啟用）：

| 固定深度 | 局數 | 平均分 | 中位數 | ≥2048 | ≥4096 | 最大方塊分布 |
|---|---|---|---|---|---|---|
| 4 | 100 | 22871 | 21852 | 53% | 5% | 最高 4096×5 |
| 5 | 100 | **45727** | 37082 | 83% | 47% | 出現 8192×3 |
| 6 | 60 | 44285 | 36342 | 80% | 38% | 出現 8192×4 |

同種子配對比較（60 局）：

- **depth 4 → 5：平均 +17687 ±3317 分，60 局裡 43 局變好** → 非常顯著，分數幾乎翻倍。
- **depth 5 → 6：平均 +3112 ±5154 分，60 局裡 30 局變好（剛好一半）** → 誤差範圍內，**等於沒有差別**。

把兩件事合起來看，結論就很清楚也很掃興：**分數大約在深度 5 就飽和，而腳本本來就已經跑在深度 6.5 了**，所以這次加速換來的 +0.9 層，預期帶來的分數增益是 ~0。

#### 那這輪到底值不值得？值得，但理由不是「分數變高」

1. **同樣的棋力只花 1/3 的 CPU**，而且是逐格驗證過的「決策完全相同」，不是近似。
2. **抗劣化的餘裕變大**：分數對深度的懸崖在 5 附近（掉到 4 直接砍半）。舊版在 122 個盤面裡已經有 6~9 次掉到深度 5；新版一次都沒有低於 6。換到比較慢的機器、背景分頁被節流、或殘局特別貴的盤面時，舊版更容易滑下懸崖，新版有約 3 倍的餘裕。
3. **把省下來的時間換成局數**（已採用，見下一節）：既然深度 5~6 就夠用，多出來的深度是白燒 CPU，不如把預算砍掉、每小時多跑好幾倍的局數。因為 2048 拚高分本質上是「操作品質 × 重試次數」，品質既然飽和，剩下的槓桿就只有重試次數。

### 5. 依實測把每步預算砍到剛好穩住飽和點

既然分數在深度 5 就飽和、而深度 6 現在只要幾十毫秒，就沒有理由再用 120ms 的預算去換那些買不到分數的深度。用 122 個真實盤面（早盤到殘局）實測各種預算實際搜到的深度：

| 設定 | 平均深度 | 最低深度 | 每步平均 | p90 | 最大 |
|---|---|---|---|---|---|
| 舊：budget=120 / ext=300 / min=4 | 7.57 | 6 | 132.0ms | 204.7ms | 316.9ms |
| budget=60 / ext=150 / min=4 | 7.21 | 6 | 74.1ms | 113.4ms | 139.2ms |
| budget=40 / ext=100 / min=6 | 7.07 | 6 | 61.7ms | 102.0ms | 125.4ms |
| **現用：budget=25 / ext=60 / min=6** | **6.65** | **6** | **31.3ms** | **57.4ms** | **77.2ms** |
| budget=15 / ext=40 / min=6 | 6.32 | 6 | 21.7ms | 33.3ms | 50.6ms |

**關鍵欄位是「最低深度」**：所有設定的最低深度都還是 6，一次都沒有掉到飽和點以下，代表這樣砍預算不會讓棋力下降——省掉的全是「深度 7~9 那段買不到分數的計算」。

採用 `SEARCH_TIME_BUDGET_MS = 25`（異常盤面延長模式 `60`）：每步搜尋從 132ms 降到 31ms（**約 4.2 倍**），最壞單步從 317ms 降到 77ms。沒有再往下砍到 15ms，是因為瀏覽器裡每步還要等 DOM 穩定（1~3 個影格、約 16~50ms），再往下砍對「每小時幾局」的實際增益已經很小，卻會把深度餘裕一起吃掉，不划算。

同時把 `MIN_GUARANTEED_DEPTH` 從 4 提到 **6**：預算砍低之後，這道硬性保證才是「強度不會掉」的真正保險——就算之後遇到特別貴的盤面或比較慢的機器，也一定會把飽和點以上那一層算完，不會退回 4 層那個懸崖下面。

#### 想再往上，只剩 heuristic 這條路

深度已經飽和，代表**真正的天花板在 `evaluate()` 的評分函式本身**，不在搜尋速度或深度。這次刻意沒有動它——`evaluate()` 編碼的是使用者本人的手動技巧（見 `攻略.md`），要換成別的評分方式屬於「改玩法」而不是「改引擎」，應該先問過本人，而且要拿同樣規模的對局實測（每個配置至少 60~100 局、同種子配對比較）才能下結論，不能憑感覺調權重。

### 6. 血淚教訓：搜尋變快之後，讀盤反而讀到「少一顆方塊」的舊盤面（已修好）

把 `SEARCH_TIME_BUDGET_MS` 從 120 砍到 25 之後，實際上場測試分數從原本能到十萬以上崩到只剩 1000~2000 分、最大方塊只有 128，盤面完全看不出角落/蛇形結構。追查後發現：

**根因不在演算法，在讀盤時機。** 讀 `script.js` 原始碼發現，這個網站按下方向鍵後的處理分兩段：現有方塊的位置是**同步**設定的（`style.left/top` 立刻更新），但真正套用結果（新方塊生成、加分）是透過 `pendingTimeoutId = setTimeout(() => applyAnimResult(...), SLIDE_MS)` 延後執行的，`const SLIDE_MS = 90`——這是網站寫死的常數，跟我們用 CSS 壓縮的動畫時長完全無關，改 CSS 不會讓它變快。

腳本原本的 `waitForBoardSettle()` 只靠「連續兩個影格 `.tile` 的 `left/top/v` 簽章都沒變化」判斷盤面穩定。因為現有方塊的位置是同步設好的，按下方向鍵後幾乎立刻就會連續兩影格沒有變化——在新方塊真正出現（90ms 後）之前，這個判斷就已經成立了。於是每一步都讀到一個「少一顆方塊」的盤面去搜尋、去判斷重骰時機，整個 `evaluate()`/角落/尾巴邏輯全部建立在錯誤的盤面上，就算演算法本身完全正確也沒用。

**這個雷本來就在，只是被「不小心」蓋住了**：以前單步搜尋要 ~130ms，比 90ms 長，等到真的要讀下一步盤面時，那個 90ms 早就過了；這次把單步壓到 ~25ms，遠低於 90ms，於是幾乎每一步都會搶在網站真正落子之前讀盤，問題才大面積爆出來。教訓：**改動生態系裡任何一個環節的時間常數之前，要盤點清楚系統裡還有哪些「假設某個步驟夠慢、所以來不及出錯」的隱性依賴**——這次的教訓是先前的效能驗證只測了單步搜尋的正確性/速度（比對決策是否一致），沒有涵蓋「搜尋變快之後，跟頁面本身既有的非同步時序還合不合得上」這一層。

**修法**：`waitForBoardSettle()` 加一道 `MIN_SETTLE_FLOOR_MS = 110`（90 加安全邊際）的硬性下限，用真正的計時器（`setTimeout`，不受分頁背景時 rAF 暫停影響）先等滿這個下限，才開始原本「連續影格穩定」的判斷。實機測試（Claude in Chrome 打開真實頁面）確認修好後盤面維持正常的角落＋蛇形結構（例：`[[0,0,0,0],[8,2,0,2],[16,4,0,0],[32,16,2,0]]`），分數正常成長，不再出現方塊數量對不上的情況。

#### 6.1 追加：這個修法一開始讓分頁不能在背景跑了（又修好了）

上面那個floor-wait本身用 `setTimeout`，沒有背景分頁問題；但「連續影格穩定」判斷那段沿用舊的 `nextFrame()`，內部是 `requestAnimationFrame`。**Chrome 對隱藏分頁的 rAF 不是節流，是直接完全暫停、永遠不觸發**——實測 `await requestAnimationFrame(...)` 在背景分頁裡卡住超過 3 秒都沒 resolve。也就是說只要分頁被切到背景，`waitForBoardSettle()` 的穩定判斷迴圈就會卡死，整個 bot 停在原地，這正是舊版（單純固定 `sleep`，從頭到尾不依賴 rAF）沒有的問題——這次的「讀盤等待」改法讓背景執行的能力整個消失了。

修法：把 `nextFrame()` 內部從 `requestAnimationFrame` 換成 `setTimeout(fn, 16)`。背景分頁裡 `setTimeout` 只會被節流（每秒 1 次甚至更慢，視分頁被隱藏多久而定），變慢但不會整個卡死，跟舊版固定 `sleep` 的背景容忍度一致。Claude in Chrome 實測確認：分頁在背景（`document.visibilityState === 'hidden'`）時，腳本仍會持續前進（20 秒內從第 8 步走到第 9 步，分數 16→24），只是明顯變慢；前景時维持原本的毫秒級速度不受影響（`nextFrame()` 的 16ms 間隔約等於一個影格）。

### 7. 使用者觀察「有些該合併的結果沒有合併」——實測結論：不是 bug，加重合併權重沒有用

使用者反饋覺得評分機制該把合併的權重提升，因為肉眼觀察到一些「感覺該合併」的盤面沒有合併。這個觀察值得認真查，但查完的結論是：**現在的權重是對的，加重合併沒有幫助**。

**先量化「skip 有多常見」**：拿 100 場完整自我對局（depth=5 固定深度，排除時間預算噪音）逐步記錄，每一步判斷「4 個方向裡有沒有任何一個會產生合併」跟「實際選的方向是不是其中之一」。結果：

- 89.8% 的決策點**當下都存在至少一個能合併的方向**（board 稍微雜一點，幾乎每步都會有某處小數字剛好相鄰相等，這件事本身很常見，不代表那是「值得」的合併）。
- 其中 18.7% 被跳過（bot 選了不合併的方向）。
- 每局的 skip 比例跟該局最終分數的 Pearson 相關係數 = **-0.258**——弱負相關，且很可能是反過來的因果：盤面越亂的局，本來就會有更多「巧合相鄰相等」的雜訊合併機會，同時分數也會越低，不是「跳過合併導致分數低」，是「盤面亂」同時導致這兩件事。相關係數這麼弱，不足以單獨當證據。

**所以真正拿去 A/B 測**：把 `TAIL_MERGE_READY_BONUS`/`BODY_MERGE_READY_BONUS` 各自加倍、加三倍，跟原始權重比較（80 場配對種子、depth=5 固定深度，同一顆種子三個版本都跑一次，直接比較同種子下的分數差）：

| 版本 | mean | median | 對比 baseline 的平均分差 | 贏的局數 |
|---|---|---|---|---|
| baseline（TAIL=6, BODY=10） | 36236 | 34690 | — | — |
| 加倍（TAIL=12, BODY=20） | 39283 | 35020 | +3047 ± 3355（配對標準誤） | 42/80 |
| 加三倍（TAIL=18, BODY=30） | 37273 | 34662 | +1037 ± 3208（配對標準誤） | 42/80 |

兩個變體的平均分差都**遠小於配對標準誤**（信心區間完全蓋住 0），贏的局數也只有 42/80（52.5%，跟丟硬幣沒有顯著差異）。更反直覺的是：**加重合併權重之後，skip 比例沒有下降，反而從 18.8% 微升到 19.5%、20.8%**——代表「多逼 expectimax 選合併」這個念頭本身沒有換到任何實際好處，甚至連「減少 skip」這個最直接的效果都沒量到。

**結論**：使用者觀察到的「該合併沒合併」大部分是 expectimax 正確的延遲合併決策——2048 的標準策略本來就是「小合併能不做就不做，優先維持蛇形/單調排列」，現在的權重已經在做這件事，不是漏算合併，是**刻意**不做某些眼前的小合併去保護結構。這不是「加重一個數字」能解決的問題，真要再進步得在 `evaluate()` 的整體結構上動刀，不是單純調高既有的合併加分——而動 `evaluate()` 結構屬於「改玩法」，這次沒有做，維持現有權重不變。

### 8. 使用者觀察「頭的第一列最後一個常卡小數字」——量出來是真的，但修它反而更差

使用者反饋：蛇形「頭」那一列（`SNAKE_RANKS_2D` 第 0 列）最後一格常年卡著小數字。對應到程式碼是 `order[3]`（rank 12，boustrophedon 路徑第一次轉彎的「肘部」，緊接在頭三格 `order[0..2]` 之後）。這次的結論比較微妙：**現象是真的，量出來確實比其他位置更常卡小數字；但去修它（加懲罰逼它清掉）反而讓分數變更差**，所以維持現狀。

**先確認現象存不存在**：40 場自我對局（depth=4 固定深度，上限 4000 步，換取跑更多局），每一步記錄 `order[1]`~`order[9]`（頭尾中間的身體區）裡「頭已經發展到 128 以上、但這格還是小於 32、而且比前一格小很多（≤1/4）」的比例：

| 位置 | 卡住比例 | 平均最長連續卡住步數 |
|---|---|---|
| order[1] | 6.3% | 34.0 |
| order[2] | 23.7% | 89.2 |
| **order[3]（使用者說的位置）** | **40.0%** | **98.2** |
| order[4] | 16.8% | 32.5 |
| order[5] | 13.6% | 21.9 |
| order[6] | 26.0% | 22.4 |
| order[7] | 24.8% | 31.0 |
| order[8] | 9.8% | 10.5 |
| order[9] | 3.3% | 5.1 |

`order[3]` 確實是 9 個身體位置裡卡住比例最高、卡住最久的一個，比次高的 `order[6]`（26.0%）還高出 14 個百分點——使用者的觀察是對的，不是錯覺。**根因也找到了**：`bodyAnomalyPenalty()` 只懲罰「遞增違規」（`order[i]` 比 `order[i-1]` 大，方向反了）；`order[2]`（頭旁邊、通常很大）掉到 `order[3]`（一格小值）是**正確方向的落差**，不論落差多大都不會被扣分，只要 `order[4]` 之後沒有比 `order[3]` 更大的值頂上來，就完全不會觸發任何懲罰——這是評分函式的一個死角，不是搜尋深度不夠。

**但這個現象跟分數的關係，方向是反的**：`order[3]` 的卡住時長跟該局分數的相關係數是 **+0.754**（原始最長連續步數）、正規化成「佔決策點比例」後仍是 **+0.470**（跟分數）、**+0.646**（跟每步平均分數，排除單純局長效應）。也就是說卡住越久/越常，分數反而越高——跟「這是問題」的直覺完全相反。合理解釋：頭部發展得越大（分數越高的局），`order[3]` 卡住的判定條件（頭 ≥128）成立的機會本來就越多、越久，這是「棋局進展到後期」的伴隨現象，不是因果。

**直接下去 A/B 驗證**（60 場配對種子、depth=4）：試著在 `bodyAnomalyPenalty()` 裡加一條「頭部已發展、`order[1..3]` 卻是小值又沒有合併對象」的額外懲罰項（懲罰量抓 `(headVal - val) * elbowScale`，因為 `weightedValue` 把大於 32 的數字放大 4 倍，頭部動輒幾千，`elbowScale` 要抓很小才不會蓋掉其他項的權重）：

| 版本 | 平均分數 | 對比 baseline 的平均分差 | 贏的局數 |
|---|---|---|---|
| baseline（不額外懲罰） | 20970 | — | — |
| elbowScale=0.02 | 16825 | **-4145 ± 2109**（配對標準誤） | 22/60 |
| elbowScale=0.08 | 11269 | **-9701 ± 2072**（配對標準誤） | 18/60 |

兩個變體都**明確變差**（平均分差遠超過配對標準誤，不是雜訊），贏的局數也遠低於一半。逼 expectimax 主動清掉 `order[3]` 的小值，代價是打亂原本更值錢的頭部/身體結構（要清掉這格通常得動用會影響 `order[1]`/`order[2]` 排列的方向），得不償失。

**結論**：使用者觀察到的現象是真的（`order[3]` 確實比其他位置更容易卡小數字，根因是 anomaly 判定只抓遞增違規、不管正確方向的落差有多大），但這是評分函式的一個**良性死角**，不是缺陷——放著不管，讓 expectimax 把它當成小值暫存格反而是對的；主動去修只會讓搜尋為了清一格小數字去犧牲更值錢的頭部結構。這次沒有改 `evaluate()`，維持現狀。

### 9. 外部分析報告建議「延後角落鎖定時機」——A/B 驗證結論：沒有效果，維持現狀

三份外部優化建議報告（A、B、C，見 [優化建議/](./優化建議/)）裡，A 跟 B 都獨立指出 `updateActiveCorner()` 在第一次呼叫 `bestMove()` 時就選角落，當時盤面幾乎是空的，四個旋轉方向的加權分數幾乎分不出高下，第一手選角落接近隨機，但選完後整局鎖死不換。B 具體懷疑這是「同一顆種子跑出 5680～110744 這麼大分數變異度」的主因，建議改成「盤面加權總和超過某門檻（例如 >64）才鎖」；A 提出類似方向，改成「觀察前 10～20 步再鎖」。兩者共同精神都是「延後鎖定的時間點，但鎖定之後一樣整局不變」，跟玩家本人「固定一個角落後就不動」的技巧並不衝突。

**實作兩個變體**，都只改鎖定的時間點，鎖定後的行為（永不再換角落）跟原本一致：

- `weighted>=64`：每次 `updateActiveCorner()` 都重新挑當下最貼合的旋轉方向，但只有盤面加權總和 ≥64 才真正鎖定（對應 B 的建議）。
- `observe15`：同樣每次重新挑最貼合的方向，但改成計滿前 15 次 `bestMove()` 呼叫才鎖定（對應 A 的建議）。
- baseline：現有行為，第一次呼叫就鎖定不變。

**A/B 測試（30 場配對種子完整跑到底，時間預算跟正式版一致，非固定深度）**：

| 版本 | 平均分數 | 中位數 | 標準差 | 對比 baseline 的平均分差 | 贏的局數 |
|---|---|---|---|---|---|
| baseline（第一手就鎖） | 46947 | 55936 | 20853 | — | — |
| weighted>=64 | 44285 | 36284 | 22305 | -2662 ± 4398（配對標準誤） | 15/30 |
| observe15 | 47507 | 47696 | 21277 | +560 ± 5141（配對標準誤） | 15/30 |

兩個變體的平均分差都**遠小於配對標準誤**（信心區間完全蓋住 0），贏的局數剛好都是 15/30（50%，跟丟硬幣沒有差異）。B 提出的「延後鎖定會降低分數變異度」的假說也沒有量到：三個版本的標準差（20853、22305、21277）幾乎一樣，延後鎖定沒有讓變異度變小，反而 `weighted>=64` 的標準差還略高一點。

**結論**：延後角落鎖定時機**沒有帶來任何可量測的改善**，B 懷疑的「開局隨機選角落導致分數暴衝暴跌」的機制沒有得到數據支持——可能原因是開局盤面雖然分數差異小，但四個旋轉方向本身互為鏡射/旋轉對稱，隨機選中任何一個造成的長期影響其實有限，真正決定分數上下限的是後續每一步的評分與搜尋品質，不是第一手選哪個角落。這次沒有改 `autoplay-bot.js`，維持現狀。

### 10. 外部分析報告建議「Chance Node Pruning 精細化」——A/B 驗證結論：沒有效果，維持現狀

三份外部優化建議報告裡，A 跟 C 都獨立指出 `search()` 的機率剪枝（`nCells > PRUNE_EMPTY_THRESHOLD` 時只留 `PRUNE_KEEP` 個 criticality 最高的空格展開 2/4 兩種分支，其餘只展開 2）在空格 6～8 的中後盤轉換期可能太激進：跳過 10% 機率的「4」分支，會讓 Expectimax 過度樂觀，沒算到「4 落在關鍵位置導致整局卡死」的風險。兩份報告給的方向不完全一樣——A 建議剪枝強度隨搜尋深度漸進調整（淺層/接近根完整展開，深層才剪）；C 建議直接把 `PRUNE_EMPTY_THRESHOLD` 從 6 提高到 8～10，或改用機率權重剪枝取代看空格數量。

**實作上先踩了一個坑**：A 的「淺層完整展開」如果字面照做（`depth` 夠大時直接不剪，`nCritical = nCells`），在空格數多的開局盤面會直接爆炸——第一手 `bestMove()` 就卡死沒有跑完（背景測試腳本掛了超過 2 分鐘、第一場遊戲的第一步都沒跑出結果，直接判定不可行、中止）。原因是 `MIN_GUARANTEED_DEPTH = 6` 以下完全不檢查時間預算，一定要跑完；拿掉剪枝等於拿掉這個安全網背後的「節點數有上限」假設，深度 4～6 的中間幾輪在空格 12～14 顆的開局盤面上，展開量會失控暴增。改成**有界版本**：新增 `DEEP_EXPAND_MIN_DEPTH`（預設 4）與 `DEEP_EXPAND_EXTRA_KEEP`（預設 4），depth ≥ `DEEP_EXPAND_MIN_DEPTH` 時 `nCritical = min(nCells, PRUNE_KEEP + DEEP_EXPAND_EXTRA_KEEP)`，一律封頂、不會超過 `PRUNE_KEEP` 加一個固定額度，才不會被寬盤面拖爆。修好後驗證：把 `DEEP_EXPAND_EXTRA_KEEP` 設回 0，跟原版逐步比對 3 個種子、共 900 步的 `bestMove()` 選擇，0 個不一致，確認新程式碼在關掉時完全等價於原版。

**A/B 測試（真實時間預算跑 `bestMove()`，非固定深度；因為單場真實對局要幾十秒，場數比照過去縮小到可在合理時間內跑完，配對種子）**：

| 版本 | 場數 | 平均分數 | 中位數 | 標準差 | 對比 baseline 的平均分差 | 贏的局數 | 耗時倍數 |
|---|---|---|---|---|---|---|---|
| baseline（現有剪枝，threshold=6/keep=6） | — | — | — | — | — | — | — |
| A+C 合併（深度漸進＋threshold=9/keep=8） | 20 | 23186 | 26426 | 6981 | -1773 ± 1693（配對標準誤） | 9/20（45%） | 1.00x |
| 僅 C（threshold=9/keep=8，不做深度漸進） | 15 | 25464 | 26832 | 4037 | +376 ± 1528（配對標準誤） | 9/15（60%） | 1.08x |

（baseline 兩次測試各自的平均分別是 24960 跟 25089，皆列在對比欄位而非重複列出。）

兩個變體的平均分差都**遠小於配對標準誤**（信心區間完全蓋住 0）。合併版甚至略偏負，標準差（6981）比 baseline（4149）大很多——單場對局的分數波動變大，最差的一場只有 2960 分（baseline 最差是 13492），代表放寬剪枝偶爾會讓某一步的評估反而挑到更差的方向，不是單純「更準但更慢」，是真的改變了選擇。僅 C 版本平均分差轉正但幅度遠小於噪訊，且速度還慢了 8%（`msPerDecision` 從 34～41 升到 44），不符合「先確認 heuristic 以外的改善不會拖慢速度」的原則。

**結論**：不管是 A 的深度漸進、C 的門檻提高，或兩者合併，在真實時間預算下都**沒有帶來可量測的改善**，維持現狀。可能原因跟第 9 節類似：搜尋深度已經在飽和點附近（見第 5 節），這裡多花的節點數換來的精度提升，不足以抵過同一時間預算下少搜一點深度的代價，兩者大致抵消。這次沒有改 `autoplay-bot.js`，維持現狀。

### 11. 外部分析報告建議「evaluate() 評分核心四項」——A/B 驗證結論：只有 Smoothness 確認有效，其餘全部維持現狀

三份外部優化建議報告（A、B、C）裡，四項建議各自被 2 份以上報告獨立提出，直接對應 `evaluate()`/`weightedValue()` 的核心評分邏輯，因此放在一起測（互相會透過總分公式互動）：

1. **Smoothness**（A、B、C 三份一致，唯一被三份都列為第一優先的項目）：在 `evaluate()` 加一項懲罰，對盤面上每一對格網相鄰（上下左右，不限蛇形路徑）且都非空的方塊，扣 `|log2(a) - log2(b)|`，乘上權重 `SMOOTHNESS_WEIGHT`。
2. **大數值權重連續化**（A、C）：把 `weightedValue()` 現有的門檻+固定倍數（`>=32` 乘 4 倍，16→16 但 32→128 有 8 倍斷層）換成連續函數 `v * log2(v)`（或 `v * log2(v)^1.5`）。
3. **空格數非線性權重**（A、B、C 三份都提到，細節不同）：把 `empties * EMPTY_WEIGHT` 換成 `empties² * EMPTY_WEIGHT_QUAD`。
4. **蛇形權重線性→指數**（A、C）：現有 `snakeValue()` 直接拿蛇形名次（0～15，線性）當權重，兩份報告建議改成指數衰減（權重 = `B^(15-名次)`，`B` 在 0.125～0.5 之間），讓角落跟次一格的權重差距從線性的「15 比 14」拉大成指數的「1 比 B」，逼 expectimax 更不願意讓最大值離開角落。

**測法**：沿用第 9/10 節的作法（把 `autoplay-bot.js` 的邏輯區塊字串抽出、灌進 vm context 跑），但這次是結構性改動（換函式本體），不是單純換常數，所以额外寫了 `loadBotFromSource()`（能直接吃修改過的原始碼字串，不用真的另存檔案）跟一套字串 patch 函式，每個變體各自對 baseline 原始碼做最小修改。固定深度 4（換取能跑更多局），30 場配對種子起步（比原訂 60～100 少，先用小樣本篩掉明顯沒救的，留時間給有希望的項目重複驗證）。

**第一輪結果（30 場配對種子，depth=4）**：

| 項目 | 變體 | 平均分差（對比 baseline） | 贏的局數 |
|---|---|---|---|
| Smoothness | weight=10 | +4652 ± 2833 | 18/30 |
| Smoothness | **weight=25** | **+11782 ± 3475** | **21/30** |
| 連續權重 | log2 | +10019 ± 3705 | 21/30 |
| 連續權重 | log2^1.5 | +2123 ± 3083 | 15/30 |
| 空格平方 | weight=1.6 | +1745 ± 2921 | 16/30 |
| 空格平方 | weight=3 | -1325 ± 2803 | 13/30 |
| 蛇形指數 | base=0.5 | **-17106 ± 2881** | **2/30** |
| 蛇形指數 | base=0.25 | **-18416 ± 2455** | **2/30** |

**空格平方**兩個權重的平均分差都遠小於配對標準誤（信心區間蓋住 0），跟第 9/10 節一樣的「沒有可量測改善」，直接淘汰。

**蛇形指數**兩個版本都是**災難級的負分**（贏率只有 2/30 ≈ 6.7%，平均分差 -17000~-18000，遠遠超過標準誤），跟 A、C 兩份報告的直覺完全相反——後續看 `tiles` 分布發現指數版遊戲平均步數只有baseline的三分之一（487/413 步 vs 1373 步），代表把角落權重拉到跟次一格差幾十倍之後，AI 會為了保護角落做出過度保守、甚至自相矛盾的選擇，很快就把自己逼死，不是「更聽話地鎖角落」，是「鎖過頭反而提早崩盤」。這是四項裡最明確、最值得記錄的一個反直覺結果。

**Smoothness（weight=25）跟連續權重（log2）兩項第一輪都像是贏家**，於是做第二輪獨立驗證（换一批種子、加一個「兩者疊加」的組合版，同樣 depth=4、30 場配對種子）：

| 版本 | 對比 baseline 的平均分差 | 贏的局數 |
|---|---|---|
| smoothness25（重複驗證） | +10583 ± 4220 | 21/30 |
| log2（重複驗證） | +1967 ± 3255 | 14/30 |
| smoothness25 + log2（疊加） | +7694 ± 2941 | 23/30 |

**Smoothness25 兩輪結果一致**（+11782/+10583，兩輪都遠超標準誤、贏率都是 21/30=70%），確認是真的改善，不是雜訊。**但 log2 沒有重現**：第一輪 +10019±3705（看起來像贏家），第二輪只剩 +1967±3255（信心區間蓋住 0，等於沒有效果）——換一批種子，同一個變體的結論就翻掉，這代表第一輪的正數多半是那批種子恰好對 log2 有利的運氣，不是真的效果。直接拿同一批種子算「疊加版 - smoothness25 單獨」的配對差，結果是 **-2890 ± 3752**（14/30 勝），確認疊加 log2 沒有在 smoothness25 之上帶來任何額外效益。

**結論與已採取的行動**：四項建議裡只有 **Smoothness（weight=25）** 通過两輪獨立驗證，其餘三項（連續權重、空格平方、蛇形指數）都沒有可量測的改善，蛇形指數甚至是明確的負面結果。已把 smoothness=25 這一項改動寫成獨立檔案 `autoplay-bot_new.js`（複製自 `autoplay-bot.js`，只加這一項，其它逐字相同，方便 diff），原本的 `autoplay-bot.js` 維持不動，是否要正式取代由使用者決定。這次的教訓跟第 7/8 節一致：**外部報告的共識（兩份以上獨立提出）只代表「值得測」，不代表「測了就會贏」**——log2 被 A、C 兩份報告獨立提出、第一輪測試也看起來像贏家，換一批種子就翻盤，沒有第二輪重複驗證的話會誤判成四項裡的第二個贏家。

## 這件事帶來的一般性心得

- **速度優化只驗證「決策本身正確」還不夠，要驗證「跟外部世界的既有時序假設還成不成立」**：這次拿舊版/新版比對搜尋決策，0 mismatch，證明演算法本身沒錯；但第 6 節那個 bug 出在「搜尋變快讓讀盤時機跟網站自己的 90ms 延遲時序對不上」，這種問題只有在**真實瀏覽器跑一整局**才驗得出來，Node 裡跑再多局都測不到，因為 Node 沒有網站的 DOM/setTimeout 時序可以踩。以後任何動到「跟真實網頁互動時機」的優化（讀盤延遲、按鍵節奏），光靠 Node 端的引擎正確性測試不夠，一定要另外開瀏覽器實機跑過。
- 不是每個網站的遊戲狀態都會像 dino 版那樣大方掛在 `window` 上；沒有的話，DOM 屬性（`dataset`、`style.left/top`）通常還是能反推出完整狀態，只是要先搞懂它的座標公式（這裡是 `tileGeometry()` 的 padding/gap/cellSize）。
- **效能優化一定要先量測再動手，而且要確認「量測環境」跟「實際執行環境」一致**：這次第一版 profiling 把腳本丟進 vm 全域作用域測，得到「`evaluate()` 是最大瓶頸」的結論，差一點就照著去優化錯的函式；改成重現原本的 IIFE closure 作用域後，`evaluate()` 從 6764ns 掉到 240ns，真正的瓶頸另有其人（見第 4 節）。作用域結構不一樣，量出來的數字就是錯的。
- **在 V8 裡別用 BigInt 做位元運算**：這個專案兩款遊戲各踩一次——2048 的盤面雜湊（BigInt 版 1796ns vs 兩個 32-bit 整數 87ns）、黑白棋的 bitboard（BigInt 版 0.55x 反而比普通陣列慢，dual-int32 才 1.73x）。BigInt 每個運算都要配置堆積物件，在熱路徑上是災難；64-bit 的東西在 JS 裡就拆成兩個 32-bit 整數用原生位元運算。
- **「更深的搜尋」不等於「更高的分數」，要實測到飽和點**：2048 這套 heuristic 在固定深度 4→5 平均分幾乎翻倍（+17687 分），5→6 卻落在誤差範圍內（+3112 ±5154）。如果沒量這條曲線，很容易把力氣一直花在「再搜深一層」上，而真正的天花板其實在評分函式。優化前先問「這個東西的邊際效益還在不在」。
- 遇到「這個隨機性能不能鑽漏洞」的問題，先去看生成隨機數的那行程式碼有沒有傳自訂的 `rng`／有沒有用弱 PRNG／種子是不是固定的——這款用的是原生 `Math.random()` 且沒有注入種子，答案就是「不能」，老實承認比硬凹更有價值。
- 找不到漏洞、又不想承認「打不過隨機性」的話，正確的路是把公開已知的遊戲技巧寫成可量化的評分函式 + 往後搜幾步（expectimax），這比臨場手動操作更穩定，也是這類「無對手、拚分數」小遊戲唯一站得住腳的「攻略」方式。
- 「隨機性讓腳本沒用」是常見的誤解：隨機只代表**單次結果**不能保證，操作品質影響的是**平均表現**跟「能不能撐到高分」的機率，兩者不衝突。設計這類自動遊玩腳本時，遇到會隨機失敗結束的遊戲，該做的是「輸了自動重來、記錄最佳成績」，而不是跑一次就把結果當成腳本有沒有用的定論。
- **「肉眼觀察到一個現象」跟「這個現象值得改權重」是兩件事，中間一定要量測**：第 7 節使用者的觀察本身沒有錯（skip 確實存在、比例還不低），但量出來的相關性很弱又可能反因果，A/B 測試也證明加重權重沒有效果。如果沒有先量「skip 到底多常見」「跟分數的關係是不是雜訊」「調權重後真的有改善嗎」這三層，直接憑觀察加重一個數字，很容易把時間花在一個看起來合理、實際上量不出效果的改動上。
